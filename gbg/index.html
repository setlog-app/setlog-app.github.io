Clinic Entity Resolver

A build for the Gangnam Beauty Guide intake test · single file, no dependencies, runs entirely in your browser ·

The product card says the hard problem is “review syndication at scale across many Korean sources, with translation + de-duplication + clinic normalisation,” and that trust signals are the moat. So I didn’t build a landing page. I built a stub of the join that everything downstream depends on: deciding that two strings are the same clinic, and deciding that two reviews are the same review. Get those wrong and every rating, price, and “verified” badge on the site is quietly wrong too.

1 · Clinic name resolution

Paste messy clinic names — one per line, source | name. These fixtures are hand-written by me to mirror the variance patterns you actually get across Naver cafés, Daum, map listings and English blogs. They are name strings only: no reviews, ratings or claims about any clinic are asserted here.

Toggle the alias table — that checkbox is the whole argument of this build. Off = pure romanisation + fuzzy matching, which is what you get if you let the algorithm decide everything at query time. On = the same algorithm with seven remembered aliases. Watch the entity count.

2 · Review de-duplication

The same testimonial gets re-posted across a café thread, a blog mirror and the clinic’s own page, usually with small edits. Naive exact-hash dedup misses all of it. This uses character 5-shingles + Jaccard, which survives light editing.

3 · The design decisions, and what they cost

Romanisation is a real signal, but it is not the answer

I implemented Revised-Romanisation properly — Hangul syllables are decomposed arithmetically (cho = (c-0xAC00)/588, etc.), not looked up in a hardcoded word list. That earns you the phonetic brands for free: 바노바기 → banobagi matches Banobagi exactly.

Then it falls over, and the way it falls over is the interesting part. English-origin brands do not romanise back to themselves: 그랜드 → geuraendeu, not grand. 아이디 → aidi, not ID. 뷰 → byu, not VIEW. No amount of fuzzy-matching bridges geuraendeu ↔ grand without also merging things that must never merge.

So the conclusion I’d take to the schema: the canonical clinic is a first-class row with an explicit alias table, seeded once per clinic and then permanent — not a key derived on the fly at query time. Romanisation + fuzzy matching is the tool that proposes merges; the alias table is what remembers them. A pipeline that recomputes similarity on every ingest is both slower and less correct than one that resolves each new surface form against a stored alias set once.

Three bands, not one threshold

A single similarity cutoff forces you to choose between silent bad merges and silent misses. Both are invisible failures, which is the worst kind. So the resolver emits three bands:

  • auto ≥ 0.72 — merge without asking.
  • review 0.50–0.72 — the only rows a human or an LLM ever sees.
  • reject < 0.50 — treat as distinct.

The point of the middle band is that it is small and countable. If it grows, that is your alert that a new source has arrived with a spelling convention you have never seen — which is exactly the failure you want to find on a dashboard rather than in a customer complaint.

Where the LLM goes — and where it must not

Translation is genuinely an LLM job: Korean beauty-clinic review prose is idiomatic and a machine-translation API mangles it. Entity resolution is not. Putting a model in the per-record hot path would be the default move and it is the wrong one:

  • Cost. Deterministic normalisation is ~microseconds and free. At 100k ingested reviews, routing every record through a model to ask “is this the same clinic?” is a recurring bill for a question a string function already answers correctly ~95% of the time.
  • Non-determinism. The same review re-ingested next week can resolve to a different clinic. Now your ratings drift with no code change and nothing in the diff to blame.
  • Untestability. I can write a fixture test for the code above and it will fail loudly when I break it. That is what makes the “verified” badge — your actual moat — something you can defend rather than hope about.

So the LLM gets the middle band only: the handful of ambiguous merge proposals, in a batch, with the decision written back into the alias table so it is never asked twice. The model’s output becomes durable data, not a runtime dependency.

What I would do next, in order

  • Blocking before comparison. Right now this is O(n²) over all pairs — fine for 30 fixtures, not for 182 clinics × every inbound mention. First pass: bucket by first romanised bigram, compare only within bucket.
  • Persist the alias table and make the middle-band queue a real review UI, so a resolved ambiguity is resolved permanently.
  • Attach source-trust weights. A café post and a clinic’s own page are not equal evidence, and since “verified” is the moat, dedup should keep the most trustworthy copy of a duplicated review, not the first one ingested. That is a product decision the algorithm shouldn’t make silently.

Honest scope

Built inside the test window, so: fixtures are hand-authored, not scraped — I did not crawl any source, and the assessment terms rule that out anyway. Nothing is persisted; there is no backend. The romaniser handles modern Hangul syllables and ignores the archaic block. The dedup threshold is tuned on these fixtures alone and would need re-tuning on real data. This is a stub that makes a design argument concrete, not a production service.
